# Восстановление прокси — 30 октября 2026

## Подтверждённая причина

На подключённом Android-телефоне долгий WebSocket через Cloudflare получает
первые 16–32 KiB, затем перестаёт передавать данные. На той же конечной точке
Linux получает 1 MiB полностью. Небольшой MTProto handshake при этом проходит,
поэтому проверка req_DH сама по себе не выявляет зависание медиа.

Отдельный тест свежих HTTP-соединений, по 8 KiB на запрос с параллелизмом 4,
получил на телефоне 1 048 576 байт за 5,688 секунды. HTTP chunked encoding
в диагностическом клиенте разобран полностью; число относится к payload.
Наблюдение согласуется с
[описанным Cloudflare ограничением в сетях РФ](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/).
Конкретный оператор/узел, применяющий ограничение, не устанавливался.

## Исправление

Rust 1.14.0 / Android 0.4.0 используют встроенный Worker с HTTP relay.
Отдельные запросы/ответы ограничены 8 KiB и используют свежие HTTP-соединения.
TCP-сессия Telegram сохраняется внутри общего SQLite-backed Durable Object;
каждая пользовательская сессия имеет независимые socket, seq/ACK и очереди.
Upload retry не дублирует запись; download retry повторяет неподтверждённые байты.
Входящие и исходящие буферы ограничены, простаивающие сессии удаляются.

Свой VPS не задействован. Legacy Worker `/apiws` сохранён для старых клиентов.
При сетевом таймауте TLS новый relay может попробовать HTTP/80; ошибка
сертификата переход не разрешает. Режим «Worker: только TLS» запрещает его.
Собственный Worker включён по умолчанию в публичных сборках по явному решению
владельца проекта; общий CF-доменный пул выключен по умолчанию.

## Проверки и границы

- Node-тесты Worker: idempotent open/upload, порядок и повтор download,
  лимиты chunk, запрет посторонних IP, изоляция сессий и idle cleanup.
- Rust-тесты: повтор частичного HTTP body без потери/дублирования данных,
  свежие соединения, запрет plaintext recovery при ошибке сертификата,
  однократная миграция настроек и сохранение пользовательского opt-out.
- Clippy с MSRV 1.89.0, Rust/JNI/desktop unit и regression tests проходят.
- Rust CI проходит нативно на Windows, Linux и macOS.
- Подписанный Android-кандидат 0.4.0 установлен поверх 0.3.1 с сохранением
  настроек. SHA-256 проверены; сертификат совпал с установленной версией.
- Пользователь подтвердил на реальном телефоне: фото и видео загружаются.
- На физическом Windows-компьютере и в мобильной сети отдельный тест
  ещё не проводился. Энергопотребление и длительная работа не измерялись.

## Следующий шаг: скорость

В текущем клиенте download в одной MTProto-сессии последовательный: один
HTTP-запрос на 8 KiB. Поэтому скорость зависит от RTT и установления TCP/TLS.
Проверить конвейер из нескольких коротких запросов с сохранением порядка,
ограниченным окном и повторами по seq. Увеличение chunk допускается только
после измерений и согласования размера с клиентом: старые клиенты принимают
не более 8 KiB, изменение серверного default нарушит их совместимость.


## Повторная проверка сториз и ускорение (кандидат 0.4.1)

После первоначального подтверждения фото/видео пользователь обнаружил паузы
в сториз и часть не запускающихся видео. Поэтому результат 0.4.0 выше
не означает, что длительное воспроизведение исправлено полностью.
Первый кандидат 0.4.1 улучшил загрузку, но пользователь всё ещё видит паузы.

В новом конвейере используются byte offsets и подтверждение непрерывно
доставленного префикса. Диапазоны загружаются параллельно, упорядочиваются
на клиенте и могут повторяться с меньшим размером без потери байтов.
Зависший первый диапазон повторяется по свежему TCP, если следующие уже
пришли. Эксперимент с жёстким сроком повтора 500 ms от начала запроса
прошёл локальные тесты и Windows CI, но ухудшил загрузку на телефоне
по подтверждению пользователя. В исходниках это поведение отменено; подписанный code 13
с возвратом транспорта code 11 собран локально, но НЕ установлен.
Прямая установка code 11 поверх code 12 отклонена Android как downgrade;
приложение и его данные не удалялись. Для проверки действительно зависшего запроса
тестовый сервер задерживает ответ на 3 s, а не на 800 ms. Это само по себе не снижает общий профиль скорости.

По требованию пользователя одна-две ошибки не уменьшают размер/окно:
повторяется прежний размер. Снижение допускается при трёх ошибках подряд
либо доле ошибок от 25% среди не менее 16 последних результатов.
Не более одного снижения в секунду; размер уменьшается на одну ступень,
после успешных передач снова допускается рост.

Синтетический native Rust-тест выполняется непосредственно на телефоне,
использует HTTP/1.1 и свежие соединения, как транспорт приложения.
Это проверка телефон → тестовый Worker, без Telegram и Durable Object.
Два полных прогона показали для 24 KiB и окна 8 примерно 1,28 MiB/s
без ошибок (16 ответов на профиль в каждом прогоне). Для 32 KiB/окно 16
результаты сильно разошлись: первый прогон 32/32 ответа, второй 18/32.
Один удачный короткий прогон не доказывает устойчивость размера.

В расширенном прогоне проверены 48, 64, 96, 128, 256 и 512 KiB при окнах
4/8/16. У каждого размера все 24 проверенных запроса завершились ошибкой
(таймаут клиента 3 s); число включает остановку заведомо нерабочего профиля
после первых 8 ошибок без одного полного ответа. Дополнительный прогон
с таймаутом 10 s также дал 24/24 таймаута для каждого из этих размеров.
При 24 и 32 KiB в нём полностью прошли по 63 из 64 ответов; по одному
запросу каждого размера завершилось таймаутом. Это наблюдение текущего пути, не глобальный лимит Cloudflare.
Кандидат согласует с Worker максимальный размер 32 KiB, сохраняет старые
8 KiB для v1-клиентов и увеличивает окно медиа максимум до 16 запросов. В публичный стабильный релиз
новые параметры пока не включены. Требуется повторная проверка сториз
на подписанном кандидате и перенос общего кода в desktop-ветку.


### Зафиксированное состояние телефона перед остановкой тестов

На телефоне остаётся подписанный кандидат **0.4.1, versionCode 12**.
Последнее уточнение пользователя: видео зависает, затем через несколько
секунд загрузка возобновляется. У code 11 паузы были реже; code 12 сначала
оценён как ухудшение. Полное исправление медиазагрузки не подтверждено.
По просьбе пользователя дальнейшие тесты выполняются **без телефона**;
проверка Windows и локальные эксперименты не являются проверкой Android.
