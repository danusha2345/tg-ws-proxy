# Лаборатория HTTP relay — 30 октября 2026

## Зафиксированный результат Android

На телефоне остаётся 0.4.1 / code 12. Последнее уточнение пользователя:
видео зависает на несколько секунд, затем передача возобновляется.
Code 11 оценён как улучшение, code 12 с более агрессивным таймером —
как ухудшение. Полное исправление не подтверждено.

Пользователь попросил прекратить тесты телефона. Code 13 с откатом
агрессивного таймера собран и подписан прежним ключом, но не установлен.
Прямая попытка downgrade на code 11 отклонена Android; данные приложения
не удалялись. Дальнейшие результаты ниже получены без телефона.

## Проверка настоящей Windows-машины

Использован существующий SSH-доступ из чата «Проверь VPN и MQTT-сервер».
VPN и настройки прокси не менялись. Запущенный `TgWsProxy_windows_x64.exe`
слушает localhost:1445, есть локальные клиентские соединения.

Через его порт и SSH-forward успешно выполнен req_pq → req_DH для DC2,
DC4 и media DC2: `ServerDHParamsOk`. Аккаунт Telegram и готовый auth key
не использовались. Это подтверждает подключение, но не длительную загрузку
медиа и не версию исполняемого файла.

На этой же Windows выполнены HTTP/1.1-запросы curl 8.10.1 / Schannel
к временному синтетическому Worker. Указаны Connection: close, no proxy;
HTTP и HTTPS измерены отдельно. Время серии включает запуск SSH-команды,
поэтому это консервативная оценка скорости всего замера.

Одиночные ответы 64–512 KiB останавливались примерно после 23–34 KiB
и завершались таймаутом 10 s. Ошибки 404 до включения workers.dev
не включены в результаты. Полная матрица: размеры 8/12/14/24 KiB,
окна 4/8/16/32. Для каждого окна выполнены как минимум две полные волны
запросов. Лучшие варианты повторены ещё три раза:

| Транспорт | Блок | Окно | Полных ответов, 3 повтора | Медиана, KiB/s |
|---|---:|---:|---:|---:|
| HTTP | 8 KiB | 32 | 189/192 | 290,5 |
| HTTP | 12 KiB | 16 | 94/96 | 187,5 |
| HTTP | 12 KiB | 32 | 192/192 | 627,1 |
| HTTP | 14 KiB | 16 | 96/96 | 423,2 |
| HTTP | 14 KiB | 32 | 191/192 | 369,8 |
| HTTPS | 8 KiB | 32 | 192/192 | 277,5 |
| HTTPS | 12 KiB | 16 | 79/96 | 69,3 |
| HTTPS | 12 KiB | 32 | 191/192 | 326,3 |
| HTTPS | 14 KiB | 16 | 96/96 | 309,0 |
| HTTPS | 14 KiB | 32 | 175/192 | 201,4 |

Редкие ошибки не исключены из времени серии и не являются основанием
запретить профиль. Например, 14 KiB × 32 по HTTP имеет 1 ошибку из 192,
но остаётся рабочим вариантом. У 24 KiB по HTTPS ошибки существенно чаще:
в первоначальной матрице полностью пришли лишь 53 из 128 ответов.

Вывод ограничен этим сетевым путём и небольшим числом прогонов.
Windows curl использует Schannel, приложение — reqwest/rustls; тестовый
Worker не включает TCP Telegram, Durable Object и медиадекодер.
Результаты не означают такую же скорость видео или гарантию для Android.

## Экспериментальная ветка codex/relay-lab

1. При наличии следующих готовых диапазонов повторяется только отсутствующий
   префикс. Остальные запросы не отменяются. Исходный и повторный запросы
   соревнуются; после доставки байтов лишние копии этого диапазона отменяются
   через AbortHandle. Поздние результаты не дублируют поток.
2. Допускаются максимум два таких повтора на один префикс. Размер не уменьшается
   из-за самого факта повтора. Политика допускает одну-две ошибки без снижения.
3. Максимальное окно медиа увеличено до 32; общий lookahead остаётся 512 KiB.
   Поэтому для больших блоков реальное число запросов автоматически меньше.
   Серверный предел и очередь не увеличены. Успехи для роста окна считаются
   отдельно: проверка нового размера блока больше не сбрасывает разгон окна.

Регрессия моделирует зависший первый запрос, медленный исправный соседний
запрос, ответы не по порядку, частичный диапазон и единичный HTTP 503.
До изменения сосед запрашивался дважды, и проверка падала. После изменения
он запрашивается один раз; все 400 000 байт совпадают с контрольным потоком.
Отдельные тесты проверяют редкие ошибки, ограничения размера Worker,
повтор частичного body и запрет обхода ошибки сертификата.

Локально проходят 91 Rust-тест (7 сетевых/платформенных проверок явно
пропущены) и строгий Clippy на MSRV 1.89.0. Автоматические проверки CI
не заменяют проверку медиа на реальном устройстве.

Эти изменения подготовлены к выпуску Rust 1.14.1 / Android 0.4.1 (code 14)
по запросу пользователя. На момент подготовки релиза они не установлены на
Windows или Android; состояние телефона выше остаётся прежним. Следующий полезный замер — реальный Rust-клиент на
Windows против синтетического range relay, затем длительная проверка медиа
с согласованным устройством. Отдельно стоит сравнить адаптацию по goodput
и задержке первого отсутствующего блока вместо одной только частоты ошибок.
