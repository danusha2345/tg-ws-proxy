# Ускорение загрузок после 1.14.0 / Android 0.4.0

## Что уже измерено

Длинное WS-соединение на телефоне останавливалось после 16–32 KiB.
Серия свежих HTTP-запросов по 8 KiB, параллелизм 4, получила 1 MiB за 5,688 с.
Это тест участка телефон → Cloudflare, не измерение скорости скачивания
конкретного Telegram-файла. Пользователь отдельно подтвердил загрузку фото/видео
в установленном подписанном Android 0.4.0.

Дополнительная матрица chunk/window через ADB не дала надёжного результата:
часть тестовых соединений завершалась до HTTP-заголовков. Эти неполные пробы
не используются для выбора нового размера фрагмента или заявления прироста.

## Приоритет 1: конвейер download

Сейчас download одной MTProto-сессии получает один фрагмент за RTT. При окне 1
верхняя граница примерно `8192 / request_time` байт/с. Окно 3–4 коротких запросов
позволяет перекрыть RTT, сохраняя отдельные TCP-соединения до Cloudflare.

Для следующего протокола:

- согласовать версию и максимальное окно при open; старым клиентам оставить v1;
- хранить несколько неподтверждённых фрагментов в DO по seq;
- подтверждать только непрерывный диапазон байтов, уже переданный локальному
  клиенту; повтор seq возвращает те же байты;
- запрашивать несколько seq параллельно, выдавать в Telegram строго по порядку;
- ограничить окно и общий объём буферов на клиенте и Worker;
- начать с media-сессий; не умножать idle polling обычных чатов;
- проверить потерю/повтор/перестановку ответов и закрытие сессии до теста на фото,
  видео и большом файле.

Это гипотеза ускорения, а не уже реализованный прирост. Стабильные 1.14.0/0.4.0
не менялись после подтверждённого исправления медиа.

## Приоритет 2: согласуемые фрагменты 12 KiB

Проверить на телефоне 8/12/14 KiB для HTTP/80 и TLS отдельно. Выбирать размер
ниже реального порога с запасом на HTTP/TLS overhead. Размер должен быть
согласован при open и храниться на уровне сессии. Нельзя просто увеличить
серверный default: клиенты 1.14.0/0.4.0 отвергают ответы больше 8 KiB.

При 12 KiB число payload-запросов на файл уменьшается примерно на треть
относительно 8 KiB, но работоспособность такого размера в этой сети ещё
не подтверждена.

## Чего избегать

Не включать обычный keep-alive или HTTP/2 для ограниченного маршрута:
много логических запросов на одном TCP-соединении снова могут упереться
в исходный порог. Не сжимать MTProto ciphertext: он уже зашифрован и практически
несжимаем. Не менять secret и не переподключать Telegram TCP на каждый фрагмент.

## Квоты

У [Workers Free](https://developers.cloudflare.com/workers/platform/limits/)
100 000 входящих запросов в сутки на аккаунт. При 8 KiB на ответ теоретический
предел payload около 781 MiB/сутки до учёта open/up/idle/close/retry. Это общий
ресурс встроенного публичного Worker. Конвейер ускоряет передачу, но не
увеличивает суточную квоту. Платный тариф автоматически не включался.

## Варианты без Cloudflare и без собственного VPS

| Вариант | Что подтверждено | Вывод |
| --- | --- | --- |
| Прямой Telegram WS/fronting | Уже поддерживается; в этой сети телефона TLS не проходит | Сохранять как первый независимый маршрут и улучшать probe/выбор endpoint, проверять доступный IPv6 отдельно |
| Fastly WebSockets passthrough | Платформа поддерживает передачу WS к origin; требуется платный аккаунт | Кандидат для внешнего WS-маршрута без VPS, но не подтверждённая бесплатная замена; покрытие всех DC потребует отдельной проверки |
| Deno Deploy | Новый runtime поддерживает полноценные сетевые API; AUP исключает forward proxy/VPN | Не предлагать как готовый публичный relay без согласования допустимого сценария с платформой |
| Vercel | Актуальная документация поддерживает WebSockets, старые статьи могут ошибочно писать обратное; AUP запрещает proxy/VPN | Технического наличия WebSocket недостаточно для рекомендации этого сервиса как Telegram relay |
| Встроенный Tor/Arti | Есть Rust API для TCP через сеть Tor | Возможный бесплатный резерв доступности без VPS, но прирост скорости медиа не установлен; требуется отдельный прототип и измерение |
